## 为什么需要检查线程绑定

需要区分三个层次：

1. `OMP_NUM_THREADS=38`：要求 OpenMP 创建 38 个线程。
2. `numactl -N 1`：允许线程在 NUMA 节点 1 的 CPU 集合内运行。
3. `OMP_PROC_BIND=true`：启用 OpenMP 线程绑定，由运行时选择位置。

前两项不保证各线程固定到不同核。未绑定时，实际观察到 38 个线程集中在一个 CPU 上轮转，
合计 CPU 利用率只有约一个核。增加绑定后，观察到线程分散至 38 个核，每个核均实际工作。
系统为何没有自动摊开负载尚未确定；不能把某项内核策略或 CPU quota 认定为原因。
不同 OpenMP 实现的默认绑定映射可能不同，应当以实测为准。

未绑定的正式 case1 在计算阶段人工中止，没有计时结果，也没有完整 case1 PASS。
没有用估算补成绩，也没有将中止标记为正确性 FAIL。

## 单变量重复对照

同一计算节点、同一二进制、同样 38 线程和 NUMA 1。
输入 1024×1024，kernel 15×15，每次进程内部计时 3 runs。
按未绑定→绑定→未绑定→绑定的顺序执行。

| 运行配置 | 第一次平均时间(ms) | 第二次平均时间(ms) | 最大误差 | 校验 |
|---|---:|---:|---:|---|
| 不设置 OMP_PROC_BIND | 665.33 | 660.75 | 0 | PASS |
| OMP_PROC_BIND=true | 16.93 | 16.93 | 0 | PASS |

按打印时间求两轮均值，加速比约 39.16。它只属于本组输入及本次环境，
包含未绑定时的线程争用开销，不是四个正式 case 的通用加速比。
四个正式 case 的完整未绑定运行没有完成，因此没有逐项的绑定前后加速比。

官方校验在性能计时之前，失败不会进入计时。实验脚本还检查输出必须包含 PASS，
不只依赖进程退出码。

## 编译器观察与下一步

GCC 10.3.1 默认目标为 armv8-a / generic。
原始代码的向量化报告为 `vectorized 0 loops`；汇编内层包含标量 `fmadd s0` 和反复写回输出的 `str s0`。
标量 FMA 不等于 NEON 向量运算。

下一次源码实验可以尝试局部 float 累加器，在一个输出积累完后再写回，减少 store 指令和别名顾虑。
它仍有逐次累加的依赖链，因此不保证更快，需要重新检查实际汇编、绝对误差和性能。
本次没有修改累加器、索引、restrict、SIMD 或编译参数。
